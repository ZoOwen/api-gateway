# Benchmark results

Generated by `bench/run.sh`. Load driven by k6 (`grafana/k6` via Docker) against
a local dummy upstream (`bench/upstream`) — not jsonplaceholder or any other
internet host, so these numbers measure the gateway, not the internet.

**Setup:** 100 VUs, 30s per scenario. Gateway backed by real local Postgres 18
and Redis (not miniredis/mocks). **One gateway process** serves every
scenario — rate-limit algorithm is chosen per API key
(`internal/limiter.Registry`, not a per-process `LIMITER_ALGO` anymore), so
the token_bucket and sliding_window keys in scenario 3 run concurrently
against the same server, which is also what makes that comparison
representative of real usage. Everything — gateway, upstream, Postgres,
Redis, k6 — ran on one machine (Windows host + Docker Desktop for k6), so
absolute numbers reflect that machine, not a production topology. Relative
comparisons between scenarios (which is the point of this benchmark) are
still meaningful.

|---|---|---|---|---|---|---|---|

429 (i.e. actually broken), not the rate-limit rejection rate.

## Reading the numbers

**Scenario 1 vs 4 — gateway overhead.** With the same 100 VUs / 30s load, the
gateway (Redis-backed token bucket + Postgres-cached auth + reverse proxy)
sustains **~1,260 req/s** against a backend that alone handles **~11,490
req/s** direct — an ~89% throughput drop. Median latency goes from 8.4ms to
13.7ms, but p99 goes from 26.6ms to 292ms (11x worse). As before, the
gateway's cost shows up far more in **tail latency and throughput ceiling**
than in typical-case latency.

**Scenario 3 — token_bucket vs sliding_window, identical load, same server,
concurrently.** Sliding window has a *lower* median (10.53ms vs 13.73ms) but
a much *worse* tail (p95 180.9ms vs 85.6ms; p99 1539ms vs 292ms — over 5x)
and lower throughput (1153 vs 1260 req/s), while both algorithms' keys are
being hit by k6 at the same time against the same running gateway and Redis.
This matches the algorithmic cost difference documented in
`internal/limiter`: token bucket's Lua script does one HSET/HMGET pair per
call; sliding window's does `ZREMRANGEBYSCORE` + `ZCARD` + `ZADD` +
`ZREVRANGE` against a sorted set that, at this throughput and a 1s window,
holds on the order of 1,000 live entries. More Redis work per call shows up
as worse tail latency under load — consistent with the previous (two-process)
run of this same comparison, now reproduced with both algorithms genuinely
concurrent on one server, which is the actual point of the per-key-algo fix.

**Scenario 2 — the denied path is not simply "faster".** The rate limiter
rejects almost every request here (limit=1 per 60s, 100 VUs hammering it), so
this measures the short-circuit path: auth (cached) → rate limit → 429,
never reaching the proxy or the upstream. It has the highest throughput of
any gateway scenario (5,615 req/s) and much tighter tails than scenario 1
(p99 48.1ms vs 292.2ms) — consistent with "skip the upstream round trip
entirely." But its **median (17.25ms) is higher than scenario 1's
(13.73ms)**, which is not what "does less work" would predict — same
counter-intuitive pattern seen in the previous run. Working hypothesis, not
confirmed: 100 VUs hitting the *exact same* rate-limit key means every
request serializes through Redis's single-threaded execution of that key's
Lua script, and at 5,600+ calls/sec against one key that queueing may cost
more than the upstream hop it's avoiding. Not isolated further — flagging it
as a real, measured, reproducible anomaly rather than a diagnosed cause, per
"don't optimize without data."

## CPU profile (scenario 1)

Captured via `/debug/pprof/profile?seconds=10` during the scenario 1 k6 run
(see `bench/k6/results/cpu_scenario1.pprof` and `..._top.txt`). Same
constraint as before: the profile duration has to stay under the server's
`http.Server.WriteTimeout` (15s) — `seconds=20` gets the connection cut with
"empty reply from server" before pprof can write the response.

Top of the flat-time profile:

```
      flat  flat%   sum%        cum   cum%
   317.57s 97.79% 97.79%    317.63s 97.81%  runtime.cgocall
     0.04s 0.012% 97.80%      4.32s  1.33%  internal/poll.execIO
     0.02s 0.0062% 97.81%      2.22s  0.68%  internal/poll.(*FD).ConnectEx.func1
     0.02s 0.0062% 97.81%     17.97s  5.53%  net.(*conn).Close
     0.02s 0.0062% 97.82%      3.73s  1.15%  net/http.(*conn).serve
     0.01s 0.0031% 97.82%      2.01s  0.62%  internal/limiter.Middleware.func1.1
     0.01s 0.0031% 97.83%    275.19s 84.74%  internal/poll.(*FD).Close
     0.01s 0.0031% 97.83%     36.07s 11.11%  net.(*netFD).dial
     0.01s 0.0031% 97.84%     33.42s 10.29%  syscall.bind
```

As in the earlier profile, `runtime.cgocall` dominates (97.8% flat this
time, vs 94.7% previously) — this is the same Windows-specific artifact:
Go's runtime dispatches socket syscalls (connect/read/write/close via IOCP)
through the calling-convention machinery pprof attributes to `cgocall`, none
of it actual C/cgo code or gateway logic. A Linux deployment would show a
different profile shape entirely.

**New in this run, worth flagging:** `internal/poll.(*FD).Close` accounts
for 84.7% of *cumulative* time, and `net.(*netFD).dial` / `syscall.bind` for
11% / 10% — i.e. a large share of the profiled work is opening and closing
file descriptors, not just using them. That's a heavier connection-churn
signature than the previous two-process run showed (which was dominated by
`net.(*netFD).connect` at 15% cumulative, with no `.Close`/`.dial` entries
large enough to appear in the top 15 at all). The plausible explanation is
the setup change itself: one gateway process now serves both algorithms'
traffic concurrently, sharing one Redis connection pool and one upstream
transport across roughly double the request volume of either algorithm
alone — more concurrent load on shared connection pools plausibly means more
pool churn (new connections dialed, old ones closed) rather than steady
reuse. This is a hypothesis from reading the profile, not something dug
into further — per the brief, this is a report, not a tuning pass. If
pursued, the next step would be checking the actual pool-size settings on
both the Redis client and the upstream `http.Transport` under this
concurrency level before changing anything.

## Transport tuning: MaxIdleConnsPerHost

Hypothesis, prompted by two things in the numbers above: the CPU profile
showing `net.(*netFD).connect` (and later, connection churn generally)
taking a disproportionate share of time, and the denied-path scenario (2,
never touches the upstream) sustaining ~4x the throughput of the
allowed-path scenario (1, always touches the upstream). `internal/proxy`
built its `httputil.ReverseProxy` without setting `Transport`, so it fell
back to `http.DefaultTransport` — whose `MaxIdleConnsPerHost` is unset,
which means [`http.DefaultMaxIdleConnsPerHost`](https://pkg.go.dev/net/http#pkg-constants) = **2**. With 100 concurrent
VUs hammering one upstream host, 2 idle connections is nowhere near enough
to keep connections warm; most requests would pay full TCP (and, for a
real HTTPS upstream, TLS) connection setup instead of reusing one.

**Step 1 — confirm before changing anything.** Read `internal/proxy/proxy.go`
and the `net/http/httputil` and `net/http` standard library source directly:
confirmed `New()` set only `Rewrite` and `ErrorHandler` on the
`httputil.ReverseProxy`, never `Transport`. `ReverseProxy.ServeHTTP` falls
back to `http.DefaultTransport` when `p.Transport == nil`
(`reverseproxy.go:333-336`), and `Transport.MaxIdleConnsPerHost` defaults to
`DefaultMaxIdleConnsPerHost = 2` when left at its zero value
(`transport.go:1041-1044`). Hypothesis confirmed before touching any code.

**Step 2 — the fix.** `internal/proxy/proxy.go` now builds its own
`*http.Transport` by cloning `http.DefaultTransport` (not rebuilding one
from scratch — dial timeout, TLS handshake timeout, HTTP/2, proxy-from-env
all stay whatever the standard library considers reasonable) and only
overriding `MaxIdleConns: 200`, `MaxIdleConnsPerHost: 200`,
`IdleConnTimeout: 90s` (same value as the default, set explicitly rather
than left implicit).

**Step 3 — re-ran scenarios 1 and 4 only** (the allowed-path and baseline
scenarios — the ones that actually exercise the upstream connection; 2 and
3 don't need re-running for this specific change), same 100 VUs / 30s, same
machine, same dummy upstream.

### Before tuning transport

| Scenario | req/s | p50 (ms) | p95 (ms) | p99 (ms) |
|---|---|---|---|---|
| 1. Gateway, token_bucket, high limit | 1260 | 13.73 | 85.61 | 292.19 |
| 4. No gateway (baseline) | 11488 | 8.42 | 16.05 | 26.59 |

### After tuning transport

| Scenario | req/s | p50 (ms) | p95 (ms) | p99 (ms) |
|---|---|---|---|---|
| 1. Gateway, token_bucket, high limit | 4645 | 20.36 | 37.71 | 50.81 |
| 4. No gateway (baseline) | 11930 | 7.92 | 14.52 | 23.84 |

Gateway throughput went from **1,260 to 4,645 req/s** — a **3.7x** increase
— and p99 latency dropped from **292ms to 51ms** — nearly **6x** better.
Baseline (scenario 4) is unchanged within run-to-run noise, as expected
(the fix only touches the gateway's outbound transport, and scenario 4
never goes through the gateway). Median latency on the gateway path actually
went *up* slightly (13.7ms → 20.4ms) even as throughput and tail latency
both improved dramatically — plausible explanation: at 3.7x the completed
requests per second, each individual VU is issuing requests back-to-back
far more often (less time blocked on connection setup between iterations),
so the *median* request is now more likely to land during a moment of real
contention for the (still finite, now 200 instead of 2) connection pool,
even though the *distribution as a whole* is dramatically better. Not
confirmed further — noting the same "don't assume a mechanism without
checking" discipline as everywhere else in this file.

This targeted, data-driven change (confirm the hypothesis first, change
exactly the thing the hypothesis pointed at, re-measure only the affected
scenarios) is the appropriate contrast to the CPU profile findings above,
which were deliberately *not* acted on without further investigation.

## Reproducing

```
bash bench/run.sh                 # VUS=100 DURATION=30s (default)
VUS=20 DURATION=10s bash bench/run.sh   # smaller/faster run
```

Requires: Docker (for `grafana/k6`), and the same local Postgres 18 + Redis
the rest of the project's tests use (`.env`'s `DATABASE_URL`/`REDIS_URL`).
